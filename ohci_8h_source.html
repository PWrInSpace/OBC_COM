68// An OHCI host controller is controlled using data structures placed in memory (RAM).
69// It needs to both read and write these data structures (as defined by the OHCI specification),
70// and this can be mentally conceptualized similar to two software threads running on
71// two different CPUs. In order to prevent a _data race_ where data gets corrupted,
72// the CPU and the OHCI host controller need to agree on how the memory should be accessed.
73// In this driver, we do this by transferring logical ownership of transfer descriptors (TDs)
74// between the CPU and the OHCI host controller. Only the device which holds the logical ownership
75// is allowed to read or write the TD. This ownership is not visible anywhere in the code,
76// but it instead must be inferred based on the logical state of the transfer.
77//
78// If dcache-supporting mode is enabled, we need to do additional manual cache operations
79// in order to correctly transfer this logical ownership and prevent data corruption.
80// In order to do this, we also choose to align each OHCI TD so that it doesn't
81// share CPU cache lines with other TDs. This is because manual cache operations
82// can only be performed on cache line granularity. In other words, one cache line is
83// the _smallest_ amount that can be read/written at a time. If there were to be multiple TDs
84// in the same cache line, they would be required to always have the same logical ownership.
85// This ends up being impossible to guarantee, so we choose a design which avoids the situation entirely.
86
